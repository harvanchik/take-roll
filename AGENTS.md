# Take Roll Maintenance

For every app change, follow LEGAL_MAINTENANCE.md. Keep the public legal documents aligned with actual application behavior; do not invent privacy guarantees or automatically rewrite contract terms. Complete and record the legal review before building or publishing. Material accepted-agreement changes need a new LEGAL_VERSION; preserve existing acceptance evidence. Presentation-only changes must not invalidate existing agreements.

The deployed Sites app and public GitHub repository must use the same current tracked source tree. Keep real account identities, seed rosters, one-off data repairs, credentials, database exports, and preview state out of application source. Test fixtures and illustrative UI examples must be synthetic. Preserve existing account access through database mappings, not source constants. Keep historical private Git commits out of the public repository. After checks and committing a release, use scripts/sync-github-source.mjs with the existing GitHub checkout, commit/push the resulting exact tree, and verify its tree hash matches the Sites release. Do not create a sanitized variant or deploy from the GitHub checkout against a different account mapping. Do not claim automatic mirroring; synchronization is an explicit release step.
